# DIVO Design System — гайд контрибьютора

Этот документ описывает, как пользоваться общими примитивами DIVO (`DivoUIKit`) и когда выносить в них что-то новое: цвета, размеры, общие компоненты.

---

## Где что лежит

Модуль: [`submodules/DivoUIKit`](../submodules/DivoUIKit/).

```
DivoUIKit/Sources/
├── DivoColorPalette.swift      # все цвета
├── DivoDesignTokens.swift      # Radius / Shadow / Spacing + applyDivoShadow
├── Components/                 # переиспользуемые UIView/UIViewController
├── Filters/                    # фильтр-контроллеры (PROJ-125)
├── Services/                   # ImageLoader, ShimmerView — живут с палитрой
└── Snackbar/                   # общий snackbar
```

Правила размещения:

- **Цвет** → `DivoColorPalette.swift`.
- **Числовая константа** (радиус, тень, отступ) → `DivoDesignTokens.swift`.
- **Общий UI-компонент** (View/ViewController) → свой подкаталог (`Components/`, `Filters/`, …).

---

## Как пользоваться существующими примитивами

### Цвета

```swift
import DivoUIKit

label.textColor = DivoColorPalette.primaryText
button.backgroundColor = DivoColorPalette.accent
separator.backgroundColor = DivoColorPalette.separatorSystem
```

Не писать `UIColor(hexString: "#FF772D")` в фичевом коде — это дубликат `DivoColorPalette.accent`.

### Радиусы / тени / отступы

```swift
view.layer.cornerRadius = DivoDesignTokens.Radius.card       // 24
stack.spacing = DivoDesignTokens.Spacing.m                   // 16
button.layer.applyDivoShadow()                               // стандартная карточная тень
button.layer.applyDivoShadow(
    opacity: DivoDesignTokens.Shadow.opacityMedium,          // 0.10
    radius: DivoDesignTokens.Shadow.radiusLarge
)
```

Шкалы (см. `DivoDesignTokens.swift`):

- **Radius**: `xs=4`, `s=8`, `m=12`, `l=16`, `pill=20`, `card=24`, `sheet=34`
- **Spacing**: `xs=4`, `s=8`, `m=16`, `l=24`, `xl=32`
- **Shadow**: `opacityLight=0.08`, `opacityMedium=0.10`, карточная — `(0, 4)` + `radius=12`; thumb — `(0, 2)` + `radius=4`

## Когда выносить, а когда — **нет**

### ✅ Выносить

- Значение встречается **в 2+ местах** и имеет общий смысл («цвет primary-текста», «радиус карточки», «отступ между блоками»).
- Значение описано в дизайн-спеке как токен (даже если пока в одном месте) — лучше сразу ввести токен.
- Компонент со стабильным API дублируется между фичами (пример: PROJ-125 — `FilterOptionsController` жил в `ModelsFeedUI` и в параллельной ветке).

### ❌ Не выносить

- Значение разовое и семантически локальное (`let chevronSize: CGFloat = 20` внутри одной ячейки).
- Три похожих места ≠ абстракция. Три — это нормально. Четвёртое встретится — тогда и вынесем (правило трёх).
- Фичевый компонент с доменными зависимостями. В `DivoUIKit` не тащим модели (`TelegramCore`, API-типы) — только презентационные параметры.
- Компонент, который используется **один раз**. Он живёт у себя в модуле — вынос будет преждевременным.

### Сигнал «пора выносить»

Дубликат файла между фичами с минорными правками. Пример паттерна из PROJ-125: контроллеры фильтров были параметризованы (`isMultiSelect`, `showSearch`, абстрактный `FilterOptionItem`) и не имели доменных зависимостей — это чистый кандидат на вынос.

## Как добавлять цвет

1. Открыть `DivoColorPalette.swift`.
2. Найти MARK-секцию по смыслу (`Brand`, `Text`, `Surfaces`, `Separators`, …). Если подходящей нет — добавить.
3. Дать **семантическое** имя, а не цветовое — по роли, а не по оттенку:

   - ❌ `orange`, `gray99`, `blue500` — привязано к внешнему виду.
   - ✅ `accent`, `secondaryText`, `separatorSystem` — привязано к роли в UI.

   Оттенок со временем может поменяться, роль — нет.

4. Синтаксис (`UIColor(hexString:)` vs `UIColor(red:green:blue:alpha:)`) — быть консистентным с соседями в той же MARK-секции. Оба валидны, смешивать в рамках одной секции не стоит.
5. Если значение не тривиально угадывается по имени (нестандартная альфа, близкий оттенок к уже существующему, специфичное место применения) — **написать doc-комментарий** со смыслом:

   ```swift
   /// Copper тёплый 0.77/0.54/0.38 — Profile/Events/Auth buttons.
   public static let accentCopperWarm = UIColor(red: 0.77, green: 0.54, blue: 0.38, alpha: 1.0)
   ```

6. Мигрировать вызовы в фичевом коде (grep по hex/rgb, заменить на `DivoColorPalette.…`).

## Как добавлять числовой токен

1. Открыть `DivoDesignTokens.swift`.
2. Добавить в подходящую `enum` (`Radius` / `Shadow` / `Spacing`). Если категория новая — заводить отдельную `public enum`, не смешивать.
3. Значение **должно вписываться в шкалу**. Если не вписывается — в фичевом коде оставить «сырое» значение + комментарий:

   ```swift
   textField.layer.cornerRadius = 23 // TODO: DS alignment — не в шкале Radius
   ```

   Это сигнал дизайн-ревью, а не разрешение жить с магической константой вечно.

4. Для функциональной группы (тень, градиент) — добавлять helper-экстеншн рядом (`applyDivoShadow`), чтобы в фиче не дублировался набор параметров.

## Как выносить общий компонент

Шаги пошагово (на примере PROJ-125):

1. **Убедиться, что у компонента нет доменных зависимостей.** Если тянет `TelegramCore`/API-модели — сначала параметризовать (принимать простые value types вроде `FilterOptionItem`), потом выносить.
2. **Создать подкаталог** в `DivoUIKit/Sources/` (`Filters/`, `Cards/`, …).
3. **Перенести файлы целиком**, не копировать. Один источник правды.
4. **Сделать `public`**:
   - класс/структуру;
   - `init(...)`;
   - публичные свойства и колбэки (`onSave`), которые потребитель присваивает извне;
   - публичные методы API (`setItems(...)` и т.п.).
   Всё остальное — `internal`/`private`.
5. **Проверить все transitive-зависимости** (помощники, подклассы, value types). Если `ControllerA` выносится, а `HelperB` используется только им — переносить и `HelperB`. Иначе цикл импортов.
6. **Удалить старые файлы из фичевого модуля.** Никаких «оставлю пока рядом для истории».
7. **В фиче добавить `import DivoUIKit`** там, где использовались перенесённые типы.
8. **Собрать**: `bazel build //Telegram:Telegram`. Все потребители должны остаться рабочими без поведенческих изменений.
9. **Добавить doc-комментарий `///`** на публичный тип и ключевые методы. Коротко, по смыслу: для чего, как колбэчить, какие ограничения.

### Публичный API — что важно

- Не протаскивать мёртвые параметры «для симметрии». Если в исходнике был параметр, который нигде не читается, — **не** делать его частью публичного API. Чистить при выносе.
- Локализованные строки (placeholder-ы, заголовки) — **параметризовать**, а не хардкодить локальный `DivoStrings.*`. В DS-модуле нет контекста «страна/роль/пол» — это знание потребителя.
- Value types в публичном API — `Equatable`/`Hashable`, если это дёшево и полезно потребителю.

## Нюанс про Bazel и скорость итераций

**Правка в `DivoUIKit` триггерит пересборку всех потребителей.** В DIVO это ~десятки модулей. Инкрементальная пересборка после изменения токена/цвета может идти минутами.

Поэтому — **не выноси в дизайн-систему то, что ты сейчас подбираешь**.

Рабочий цикл:

1. Пока **крутишь значение** (радиус, отступ, оттенок) — держи его **хардкодом по месту**, прямо в файле фичи. Пересобирается только этот файл, итерация — секунды.
2. Когда значение **зафиксировано** (прошло ревью дизайна, выглядит ок) — **только тогда** выноси в `DivoColorPalette`/`DivoDesignTokens` отдельным коммитом.

```swift
// Пока подбираешь — так:
container.layer.cornerRadius = 18

// Зафиксировал → попал в существующую шкалу (16 = Radius.l), стало:
container.layer.cornerRadius = DivoDesignTokens.Radius.l
```

Если зафиксированное значение **не** попало в шкалу (например, 18 — между `l=16` и `pill=20`) — это повод договориться с дизайном: либо округлить до ближайшего токена, либо расширить шкалу (`DivoDesignTokens.Radius`) новым семантическим именем. Новое имя — тоже отдельным коммитом.

Чеклист перед выносом:

- [ ] Значение перестало меняться по 5 раз в день.
- [ ] Его использует хотя бы ещё одно место (или дизайн подтвердил, что будет переиспользоваться).
- [ ] Это отдельный коммит, а не попутная правка внутри фичи.

Обратное направление тоже бывает: если видно, что текущий токен кто-то начал «под себя подкручивать» (`Radius.card + 2`, `Spacing.m - 4`) — это сигнал, что в шкале не хватает значения, а не что его надо заводить на ходу. Сначала договориться с дизайном, потом коммитом расширить шкалу.
