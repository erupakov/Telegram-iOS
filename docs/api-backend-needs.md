# Доработки Backend API по результатам ревью iOS-клиента

Дата: 2026-04-06

Ниже перечислены места, где текущее API вынуждает клиент делать работу, которая должна выполняться на сервере, либо отсутствуют нужные параметры/эндпоинты.

---

## 1. Нет фильтрации событий по пользователю

**Серьёзность:** Критическая

**Что делает iOS сейчас:**
Запрашивает `POST /event/list` (все события), затем фильтрует на клиенте:
```swift
let items = response.data.items.filter({ ($0.creator?.id ?? $0.user?.id) == self.userID })
```

**Что нужно от бэкенда:**
Добавить параметр `userId` (или `creatorId`) в `POST /event/list`, чтобы фильтрация происходила на сервере.

Альтернатива: отдельный эндпоинт `GET /user/{userId}/events`.

**Влияние:** Клиент скачивает потенциально сотни событий, чтобы показать несколько штук.

---

## 2. N+1 запросов при загрузке событий профиля

**Серьёзность:** Критическая

**Что делает iOS сейчас:**
1. `POST /event/list` — получает список событий (краткие данные)
2. Для каждого события делает отдельный `GET /event/{id}` за полными данными

Если у пользователя 10 событий = 11 HTTP-запросов.

**Что нужно от бэкенда (одно из):**
- Возвращать полные данные события прямо в `POST /event/list` (включая place, файлы, фильтры моделей)
- Добавить batch-эндпоинт `POST /event/batch` принимающий массив ID
- Добавить параметр `detailed=true` в `/event/list`

**Влияние:** Множественные запросы замедляют загрузку профиля, нагружают сервер.

---

## 3. Нет фильтрации публикаций по типу медиа

**Серьёзность:** Высокая

**Что делает iOS сейчас:**
Запрашивает `POST /publication/list`, получает все публикации, потом фильтрует на клиенте:
```swift
let videoItems = response.data.items.filter { item in
    item.files.contains { MediaFormatValidator.isVideo($0.fileExtension) }
}
```

**Что нужно от бэкенда:**
Добавить параметр `mediaType` (video / image / all) в `POST /publication/list`.

**Влияние:** Клиент скачивает метаданные всех публикаций (фото + видео) чтобы показать только видео.

---

## 4. Нет облегчённого эндпоинта для статистики engagement

**Серьёзность:** Средняя

**Что делает iOS сейчас:**
Запрашивает `GET /user/engagement?offset=0&limit=1` — тянет по одному элементу из каждой категории (liked, viewed, followed) только ради поля `totalCount` в пагинации.

**Что нужно от бэкенда (одно из):**
- Отдельный эндпоинт `GET /user/{userId}/engagement-stats` возвращающий только счётчики: `{ likes: 42, views: 100, saves: 15 }`
- Поддержка `limit=0` в текущем эндпоинте (возвращать пагинацию без items)
- Включить счётчики в ответ `/user/info` или `/user/{id}`

**Влияние:** Лишний трафик — скачиваются ненужные элементы ради одного числа.

---

## 5. Нет серверной сортировки событий

**Серьёзность:** Средняя

**Что делает iOS сейчас:**
После загрузки событий сортирует их на клиенте по дате:
```swift
let sortedEvents = eventDataArray.sorted { event1, event2 in
    guard let date1 = self.parseEventDate(event1.originalDate),
          let date2 = self.parseEventDate(event2.originalDate) else { return false }
    return date1 > date2
}
```

**Что нужно от бэкенда:**
Добавить параметры `sortBy` (date, title, etc.) и `sortOrder` (asc / desc) в `POST /event/list`.

**Влияние:** Клиент дублирует логику сортировки, рискуя рассогласованием с сервером.

---

## 6. Один эндпоинт для разных операций обновления профиля

**Серьёзность:** Средняя

**Что делает iOS сейчас:**
`POST /user/update-profile` используется для:
- Обновления основных данных (имя, день рождения, пол)
- Обновления параметров внешности (рост, вес, цвет волос)
- Обновления соцсетей (Instagram, TikTok, YouTube, Telegram, Website)
- Обновления аватара
- Обновления профиля агентства (через `/agency/update`, но аватар/обложка — всё равно через этот)

При обновлении соцсетей `nil` приходится конвертировать в пустую строку `""`, т.к. неясен контракт API.

**Что нужно от бэкенда:**
Разделить на специализированные эндпоинты:
- `POST /user/profile` — основные данные
- `POST /user/social-links` — соцсети
- `POST /user/appearance` — внешность
- `POST /user/avatar` — аватар

Либо задокументировать чёткий контракт: принимает ли `null` для удаления поля, или нужна пустая строка?

**Влияние:** Разные экраны используют один и тот же endpoint по-разному; сложно версионировать и поддерживать.

## 7. Feedline: непоследовательная структура ответа для изображений

**Серьёзность:** Средняя

**Что делает iOS сейчас:**
Основное изображение ищется в массиве `files`, а если его там нет — используется отдельное поле `searchImage` как fallback:
```swift
let mainURL = item.files.first.flatMap { URL(string: $0.fullUrl) }
let avatarURL = item.searchImage.flatMap { URL(string: $0.fullUrl) }
```

Дополнительно есть нормализация, которая сортирует файлы (фото перед видео) и подставляет `searchImage` если `files` пуст.

**Что нужно от бэкенда:**
- Всегда включать основное изображение в массив `files` с явным типом (`type: "cover"` / `type: "avatar"`)
- Убрать необходимость в поле `searchImage` как отдельном fallback

**Влияние:** Сложная клиентская логика обработки двух разных источников изображений.

---

## 8. Upload: ответ не содержит созданный объект

**Серьёзность:** Низкая

**Что делает iOS сейчас:**
При загрузке фото/видео клиент создаёт placeholder с `id: -1` и вставляет его в UI до получения ответа от сервера. После загрузки заменяет placeholder реальными данными.

```swift
let placeholder = UserPhoto(id: -1, photo: UserFile(fileName: "", fullUrl: nil, ...), ...)
galleryPhotos.insert(placeholder, at: 0)
```

**Что нужно от бэкенда:**
Ответ на `POST /user-gallery/add` и `POST /publication/create` должен возвращать полный созданный объект (с ID, URL файла, датой создания) — чтобы клиент мог сразу использовать реальные данные без placeholder-ов.

**Влияние:** Клиент вынужден использовать магические значения и дублировать логику подстановки.
